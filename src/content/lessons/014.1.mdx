## Big idea

An **operating system** (OS) sits between the programs you run and the hardware. Windows, macOS and Linux are all operating systems. Strictly, **Linux** is only the **kernel**, the core that talks to the hardware. A **distribution** (distro) bundles that kernel with a shell, tools, a desktop and a package manager: Debian, Ubuntu, Fedora and many more. When people say "I run Linux", they mean a distribution.

The big differences from the other two:

| | Windows | macOS | Linux |
|---|---|---|---|
| Who makes it | Microsoft | Apple | Many projects and companies; the kernel is developed openly |
| Cost and licence | Paid, closed source | Comes with Apple hardware, mostly closed source | Free, open source: you may use, study, change and share it |
| Runs on | Most PCs | Apple computers only | Almost anything: PCs, servers, phones, routers, Raspberry Pis |
| Choice | One vendor's editions | One vendor's releases | Hundreds of distributions and several desktops |
| Software install | Installer files (`.exe`, `.msi`) and the Microsoft Store | Disk images and installer packages (`.dmg`, `.pkg`) and the App Store | A package manager that fetches packages (`.deb`, `.rpm`) from the distribution's repositories (see [lesson 011.2](/learn/011.2)) |

Linux and macOS are both Unix-like, so the command line feels similar. macOS is built on **Darwin**, Apple's open-source core, which grew out of the BSD family of Unix systems; Linux was written separately and shares no kernel code with it. Windows differs most: drive letters (`C:\`) instead of one tree, and `\` instead of `/` in paths.

Ask the guest which kernel and distribution it runs:

```bash
uname -s
```

```output
Linux
```

## Walkthrough

<ExamOnly exam="010-200">

### Installation media and ISO files

To install Linux you first need the installer. Distributions publish it as an **ISO file**, a single file that is an exact copy of an optical disc (`.iso`). You download it, then put it on **installation media**: a USB stick (most common today) or a DVD. You boot the computer from that medium, usually by pressing a key at power-on to open the boot menu, and the installer starts. Many ISOs are also **live images**: you can try the system from the stick without changing the disk.

An ISO holds the installer's files and the boot information, so a computer can start from it. To get it onto a USB stick you must **write the image to the stick**: simply copying the `.iso` file onto it as an ordinary file gives a stick that won't boot. Graphical tools do this for you (Fedora Media Writer, balenaEtcher, Rufus on Windows), and on Linux `dd` does it. The next command overwrites the whole target device, so check its name with `lsblk` first:

```bash static
sudo dd if=debian-12.iso of=/dev/sdb bs=4M status=progress
```

Two good habits: check the download against the **checksum** the project publishes (a corrupt or tampered ISO is a risk), and choose the right **architecture** (a 64-bit PC needs the `amd64` ISO, a Raspberry Pi needs an ARM image).

An ISO can also be used without any physical medium: a virtual machine can boot straight from it.

### Operating system images

An **OS image** is a ready-made copy of an installed system on disk, not an installer. You copy it to a disk or SD card and boot it, without clicking through an installation. Examples: the image you write to a Raspberry Pi's SD card, a cloud provider's "Debian 12" image, or a container image. The installer wizard is skipped, so the system is up in seconds. Images are why cloud servers start so fast.

### Installing Linux on a computer

The installer asks the same questions on most distributions:

1. Language, keyboard layout and time zone.
2. **Partitioning**: use the whole disk, or share it with another system. Partitions are explained in [lesson 014.2](/learn/014.2).
3. A computer name (hostname) and a user account with a password.
4. Which software to install, for example a desktop and its tools.
5. Where to put the **boot loader** (GRUB is the usual one). It runs first at power-on and loads the kernel.

Reboot, remove the USB stick, and the new system starts.

### Dual boot

**Dual boot** means two operating systems on one computer, and you choose one at every start. At TuxPixel, Jonas's laptop has Windows for his drawing tablet's driver and Linux for everything else. The installer shrinks the Windows partition to make room, and the boot loader shows a menu at power-on. Only one system runs at a time, and each can read files from the other's disk only with extra help. Back up before you resize partitions.

### Installing Linux in a virtual machine

A **virtual machine** (VM) is a pretend computer, run as a program inside your normal system by software such as VirtualBox, VMware or KVM. You give it some memory, a virtual disk and an ISO, and it installs Linux inside the window. Nothing happens to your real disk, so it is the safest way to practise, and you can throw it away. The terminal in this app is a tiny VM too, in your browser. The cost: the VM shares the real machine's memory and CPU, so it is slower.

### Windows Subsystem for Linux

**WSL** (Windows Subsystem for Linux) is a Windows feature that runs a Linux environment on Windows, without a separate VM window or dual boot. You pick a distribution such as Debian or Ubuntu, get a Linux shell, and can run command-line tools like `grep` or `bash` and Linux programs next to Windows ones. The current version, **WSL 2**, runs a real Linux kernel in a lightweight utility virtual machine, which gives full compatibility; older **WSL 1** translated Linux calls to Windows instead. TuxPixel's producer uses WSL to run the build tools on her Windows laptop. Source: Microsoft's WSL documentation (linked below).

### Using Linux in cloud instances

A **cloud instance** is a virtual server you rent from a cloud provider by the hour. You choose a size (CPUs, memory), an OS image and a region, and it starts in a minute. No installer, no ISO: the image is copied to a virtual disk. Linux dominates here: it is free, scriptable and light.

Provisioning means setting the new server up for its job. On first boot, a tool such as **cloud-init** reads **user data** you supplied with the instance and applies it: it can create user accounts, inject your **SSH public key** (so you log in without a password, see [lesson 015.1](/learn/015.1)), set the hostname and install software. TuxPixel runs its build server and the "Pixel Raiders" test server as cloud instances, and Ada creates a new one from the same image and user data whenever a fresh machine is needed. You then connect with SSH and work on the command line.

The usual workflow: at creation you pick or upload your **SSH key pair**'s public half, and later you log in with the private half instead of a password. You manage the instance in the provider's web dashboard, with its command-line tool or through its **API** (the way Ada's scripts do it): you can start, stop, resize or delete it. Billing is **pay per use**, so a stopped or deleted instance stops costing compute, and TuxPixel only runs the big build server while a build is going. Note that a **container** is lighter than a VM: it shares the host's kernel instead of running its own.

### Choosing an operating system (exam 010-160)

This older exam asks you to choose a system for a task, so know the trade-offs.

**GUI versus command line.** A **graphical user interface** (GUI) uses windows, icons and a mouse. The **command line** is text commands in a shell. Most desktop Linux users use a GUI, but servers (and cloud instances) are normally run through the command line: it needs less memory, can be scripted and works over a slow SSH link. Linux lets you have both.

**Desktop configuration.** The desktop environment is a separate choice from the distribution. GNOME, KDE Plasma and Xfce are common ones, and a distribution usually offers several. Changing the look, keyboard layout, panels and default programs is done in the desktop's settings program, and per-user settings are stored as files in the home directory. You can install another desktop and pick it at the login screen.

**Distribution life cycle management.** Every release is supported only for a limited time. Debian publishes a new **stable** release about every two years. The **LTS** (long-term support) releases of Ubuntu come every two years and get updates for five years. Plan an upgrade to a newer release before support ends, because after that there are no security fixes. Compare **fixed releases** (Debian stable, Ubuntu: a new version now and then) with **rolling releases** (Arch: updated continuously, no big version jump).

**Maintenance cycles, beta and stable.** A **stable** release is the one considered ready for production: it gets only bug and security fixes. A **beta** is a pre-release for testing, which may have bugs, so don't run it on the build server. Release cycles differ: Ubuntu every six months, Fedora about every six months, Debian when it is ready. Choose by how much change you accept: servers want stable, long-lived releases, a hobby laptop may want newer software.

## Exam traps

<Callout title="Linux is the kernel, a distribution is the whole system">
  <p>Debian, Ubuntu and Fedora are distributions. Linux itself is only the kernel. A distribution adds tools, a package manager and often a desktop.</p>
</Callout>

<ExamOnly exam="010-200">

<Callout title="An ISO is an installer, an image is an installed system">
  <p>An ISO file is a disc copy used to install, from a USB stick, DVD or a VM's virtual drive. An OS image is a system that is already installed, and you boot it directly (SD card, cloud instance).</p>
</Callout>

<Callout title="Dual boot is not a virtual machine">
  <p>With dual boot only one system runs at a time, and the boot loader chooses at power-on. In a VM, both systems run at once, one inside the other.</p>
</Callout>

<Callout title="WSL is not dual boot">
  <p>WSL runs Linux inside Windows, with no restart. WSL 2 uses a real Linux kernel in a lightweight VM, WSL 1 translates the calls.</p>
</Callout>

<Callout title="Cloud instances are provisioned, not installed">
  <p>A cloud instance starts from an image, and cloud-init applies your user data on first boot (accounts, SSH keys, packages). You do not click through an installer.</p>
</Callout>

</ExamOnly>
