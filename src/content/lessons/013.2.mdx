## Big idea

Linux has hundreds of small commands, and each does one job. The trick is to **connect** them. Commands connect through **streams** of text, and the shell decides where those streams come from and go to. Every running command has three:

| Name | Number (file descriptor) | Normally connected to | Used for |
|---|---|---|---|
| **standard input** (stdin) | `0` | the keyboard | the data a command reads |
| **standard output** (stdout) | `1` | the screen | the normal results |
| **standard error** (stderr) | `2` | the screen | error and warning messages |

A **file descriptor** is just the number a program uses for a stream. Output and errors both land on your screen, so they look the same, but they are two separate streams, and that matters when you redirect.

**Redirection** points a stream at a file instead of the screen or the keyboard. A **pipe** points the output of one command straight into the input of the next. With both, a few tiny tools together answer questions like "how many errors are in the build log?" in one line.

## Walkthrough

### Redirecting output: > and >>

`>` sends standard output into a file. If the file exists it is **replaced** (emptied first). If it doesn't exist it is created. `>>` **appends** to the end instead.

Ada's nightly build writes `build.log`. Mira pulls the error lines out into a new file:

```bash fixture=data-buildlog
grep ERROR build.log > errors.txt
cat errors.txt
```

```output
ERROR missing file sounds/boom.ogg
ERROR link failed: undefined reference to player_jump
```

`grep` printed nothing on screen: its output went into `errors.txt`. (`cat` shows a file, more on it below.) Now add the warnings to the same file with `>>`:

```bash fixture=data-buildlog
grep ERROR build.log > errors.txt
grep WARN build.log >> errors.txt
cat errors.txt
```

```output
ERROR missing file sounds/boom.ogg
ERROR link failed: undefined reference to player_jump
WARN texture hero.png is not 32x32
WARN unused variable speed in enemy.c
```

The difference is easy to see with `echo`, which prints its arguments:

```bash
echo first > f
echo second > f
echo third >> f
cat f
```

```output
second
third
```

The second `>` wiped out `first`. This is a classic way to lose data: `>` has no "are you sure?". (`>` is really shorthand for `1>`: output is stream number 1.)

### Redirecting errors: 2>, 2>&1 and &>

Error messages travel on stream 2, so `>` alone doesn't catch them. Here `ls` is asked about a file that doesn't exist and one that does:

```bash fixture=data-buildlog
ls nothere build.log > out.txt
```

```output
ls: cannot access 'nothere': No such file or directory
```

The good result went into `out.txt`, but the error still showed up on screen. `2>` sends the **errors** to a file:

```bash fixture=data-buildlog
ls nothere build.log > out.txt 2> err.txt
echo "out.txt holds:"
cat out.txt
echo "err.txt holds:"
cat err.txt
```

```output
out.txt holds:
build.log
err.txt holds:
ls: cannot access 'nothere': No such file or directory
```

Like `>>` for output, `2>>` **appends** errors to a file instead of replacing it. Run a command twice and both complaints are kept:

```bash fixture=data-buildlog
ls nothere 2>> err.txt
ls missing 2>> err.txt
cat err.txt
```

```output
ls: cannot access 'nothere': No such file or directory
ls: cannot access 'missing': No such file or directory
```

To put both streams in the same file, send errors to wherever output goes: `2>&1` means "make stream 2 point where stream 1 points". Bash also has the short form `&>`:

```bash fixture=data-buildlog
ls nothere build.log &> both.txt
cat both.txt
```

```output
ls: cannot access 'nothere': No such file or directory
build.log
```

The **order matters** in the long form: write `> file 2>&1`, not `2>&1 > file`. The shell reads left to right. In `2>&1 > out.txt`, stream 2 is first pointed at the screen (where 1 is right now), and only afterwards is stream 1 moved to the file. The error then stays on the screen:

```bash fixture=data-buildlog
ls nothere build.log 2>&1 > out.txt
```

```output
ls: cannot access 'nothere': No such file or directory
```

The special file **`/dev/null`** swallows everything written to it and is always empty when read. It's the bin for output you don't want, such as noisy errors:

```bash fixture=data-buildlog
ls nothere build.log 2> /dev/null
echo "exit status: $?"
```

```output
build.log
exit status: 2
```

(The exit status 2 is `ls` telling the shell that something went wrong; the next lesson covers `$?`.)

### Redirecting input with `<`

`<` makes a command **read** from a file instead of the keyboard. Many commands accept a file name as well, so it matters less than `>`, but it exists, and `wc -l < file` is a handy way to print a count without the file name:

```bash fixture=data-buildlog
wc -l build.log
wc -l < build.log
```

```output
9 build.log
9
```

In the first, `wc` opens the file by name and prints the name too. In the second, the shell opens the file and `wc` just reads its input, so it doesn't know the name.

### Pipes: |

A **pipe**, written `|`, connects the standard output of the command on the left to the standard input of the command on the right. There's no temporary file. The right-hand command starts working as soon as data arrives:

```bash fixture=data-buildlog
grep ERROR build.log | wc -l
```

```output
2
```

Pipes can be chained as long as you like, and each stage only has to do one small job. Pipes carry **stdout only**. Error messages still go to the screen unless you add `2>&1` to the left-hand command. A pipe is not the same as `>`: `>` ends in a **file**, `|` ends in a **command**.

`tee` is a pipe fitting that copies its input into a file **and** passes it on, so you can save an intermediate result:

```bash fixture=data-buildlog
grep ERROR build.log | tee errors.txt | wc -l
cat errors.txt
```

```output
2
ERROR missing file sounds/boom.ogg
ERROR link failed: undefined reference to player_jump
```

### Looking at files: cat, head, tail and less

`cat` (from *concatenate*) prints files one after the other. With one file it just shows it, and `-n` numbers the lines:

```bash fixture=data-buildlog
cat -n build.log | head -n 3
```

```output
     1	INFO compiling src/main.c
     2	INFO compiling src/player.c
     3	WARN texture hero.png is not 32x32
```

`head` shows the **first** lines (10 by default) and `tail` shows the **last** ones. `-n` sets how many:

```bash fixture=data-buildlog
head -n 2 build.log
echo ---
tail -n 2 build.log
```

```output
INFO compiling src/main.c
INFO compiling src/player.c
---
ERROR link failed: undefined reference to player_jump
INFO build finished with 2 errors
```

`head -2` is accepted as a short form of `head -n 2`. `tail -n +8` is a special form: it starts at line 8 and prints to the end. It's handy for skipping a header line (`tail -n +2`). Keep `tail` in mind for logs: the newest lines are at the end of a log.

For a log that is still being written, `tail -f build.log` keeps running and prints new lines as they arrive; press Ctrl+C to stop it. It never ends by itself, so it can't run in a lesson cell:

```bash static
tail -f build.log
```

`less` is a **pager**. For a long file it shows one screen at a time and lets you move around. It's interactive, so it can't run in a lesson cell:

```bash static
less build.log
```

Inside `less`: **Space** (or `f`) goes one page down, **b** one page back, the arrow keys move line by line, **/word** searches forward for "word" (then **n** jumps to the next match), **g** goes to the start, **G** to the end, and **q** quits. Man pages use `less`, so these keys work there too. Try it in the [terminal](/terminal).

A related filter, `tr`, translates or deletes single characters. Unlike the tools above it takes **no file name**: it reads only standard input, so you feed it with `<` or a pipe. `tr -d` deletes the listed characters and `tr -s` squeezes runs of a repeated character into one:

```bash fixture=data-playtest
tr -d 'aeiou' < enemies.txt | head -n 3
echo "slime    goo" | tr -s ' '
```

```output
slm
bt
gbln
slime goo
```

### Counting with wc

`wc` (*word count*) counts **l**ines, **w**ords and bytes (**c**haracters) in its input:

```bash fixture=data-buildlog
wc build.log
wc -l build.log
```

```output
  9  41 304 build.log
9 build.log
```

Without options you get lines, words and bytes, in that order. `-l`, `-w` and `-c` ask for one count each. In pipelines `wc -l` is the usual way to answer "how many?".

### Sorting with sort

`sort` puts lines in order. With no options it's **alphabetical**:

```bash fixture=data-playtest
sort enemies.txt
```

```output
bat
bat
ghost
ghosts
goblin
goblin
skeleton
Skeleton
slime
slime
slime
```

Useful options:

| Option | Meaning |
|---|---|
| `-r` | **r**everse the order |
| `-n` | compare as **n**umbers, not as text |
| `-k N` | sort by field (**k**ey) number N, counting from 1 |
| `-t C` | the field **t**erminator (separator) is the character C |

Numbers need `-n`. As text, `1100` sorts before `700` because `1` comes before `7`. `playtest.csv` has comma-separated fields, so `-t,` and `-k3` say "sort by the third field", the score:

```bash fixture=data-playtest
tail -n +2 playtest.csv | sort -t, -k3 | head -n 3
echo ---
tail -n +2 playtest.csv | sort -t, -k3 -n | head -n 3
```

```output
jonas,3,1100,7
mira,1,1200,2
mira,2,1500,3
---
jonas,2,700,9
jonas,1,950,5
jonas,3,1100,7
```

(`tail -n +2` strips the header line first.) Add `-r` for the highest scores first:

```bash fixture=data-playtest
tail -n +2 playtest.csv | sort -t, -k3 -n -r | head -n 3
```

```output
mira,3,2600,4
ada,1,2100,0
ada,2,1800,1
```

### Cutting columns with cut

`cut` extracts **parts of each line**. Choose the separator with `-d` (**d**elimiter) and the fields with `-f` (**f**ields), counting from 1. `-f1,3` takes fields one and three, and `-f2-4` takes a range:

```bash fixture=data-playtest
cut -d, -f1,3 playtest.csv | head -n 3
```

```output
player,score
mira,1200
jonas,950
```

The default delimiter is a Tab, not a space or a comma, so a comma-separated file needs `-d,`. `-c` selects by **c**haracter position instead of fields:

```bash fixture=data-playtest
cut -c1-4 playtest.csv | head -n 3
```

```output
play
mira
jona
```

### Removing duplicates with uniq

`uniq` collapses **neighbouring** duplicate lines into one. The word "neighbouring" is the catch: it only compares a line with the one directly before it. Duplicates that are far apart survive, so you nearly always run `sort` first:

```bash fixture=data-playtest
uniq enemies.txt | head -n 4
echo ---
sort enemies.txt | uniq
```

```output
slime
bat
goblin
slime
---
bat
ghost
ghosts
goblin
skeleton
Skeleton
slime
```

`-c` puts the **count** in front of each line, which turns `sort | uniq -c` into a frequency table. Add `sort -rn` to put the most common first:

```bash fixture=data-playtest
sort enemies.txt | uniq -c | sort -rn | head -n 3
```

```output
      3 slime
      2 goblin
      2 bat
```

Two more: `uniq -d` prints only the lines that **were** repeated, and `uniq -u` only the lines that appeared once. (`sort -u` is a shortcut for `sort | uniq`.)

</ExamOnly>

### Searching with grep

`grep` prints the lines that **match a pattern**. The name stands for "global regular expression print". You give it the pattern, then the file (or you pipe text into it):

```bash fixture=data-buildlog
grep ERROR build.log
```

```output
ERROR missing file sounds/boom.ogg
ERROR link failed: undefined reference to player_jump
```

Common options:

| Option | Meaning |
|---|---|
| `-i` | **i**gnore upper and lower case |
| `-v` | in**v**ert: print the lines that do **not** match |
| `-c` | **c**ount the matching lines instead of printing them |
| `-n` | show the line **n**umber before each match |
| `-r` | **r**ecursive: search every file below a directory |
| `-E` | use extended regular expressions (see below) |

```bash fixture=data-buildlog
grep -n ERROR build.log
echo ---
grep -c WARN build.log
echo ---
grep -v INFO build.log
echo ---
grep -i HERO build.log
```

```output
5:ERROR missing file sounds/boom.ogg
8:ERROR link failed: undefined reference to player_jump
---
2
---
WARN texture hero.png is not 32x32
ERROR missing file sounds/boom.ogg
WARN unused variable speed in enemy.c
ERROR link failed: undefined reference to player_jump
---
WARN texture hero.png is not 32x32
```

`-r` takes a directory instead of a file, and prefixes every match with the file name. If you forget the directory, `grep -r` searches the current one:

```bash fixture=data-buildlog
mkdir logs
cp build.log logs/monday.log
cp build.log logs/tuesday.log
grep -r hero logs
```

```output
logs/monday.log:WARN texture hero.png is not 32x32
logs/tuesday.log:WARN texture hero.png is not 32x32
```

`grep` is **case-sensitive** unless you add `-i`: `grep error build.log` finds nothing, because the log says `ERROR`. And quotes: when the pattern holds characters the shell treats specially (`*`, `?`, `|`, spaces, `$`), put it in **single quotes** so `grep` receives it unchanged.

### Regular expressions

Plain words are the simplest pattern. A **regular expression** (regex) adds **special characters**, so one pattern can stand for many different strings. These are the four the objective names, plus two anchors:

| Pattern | Matches | Example |
|---|---|---|
| `.` | any **one** character | `s.ime` matches `slime` |
| `[abc]` | **one** character out of the set | `[sb]at` matches `bat` |
| `[a-z]` | one character from a **range**; `[^abc]` is "anything except those" | `[0-9]` is a digit |
| `*` | the item **before** it, **zero or more** times | `go*blin` matches `gblin`, `goblin`, `gooblin` |
| `^` | the **start** of the line | `^s` matches lines starting with `s` |
| `$` | the **end** of the line | `t$` matches lines ending with `t` |

Careful: in a regular expression `*` means "repeat the previous item", **not** "anything". Anything, any length, is `.*` (any character, zero or more times). That differs from the file globs of [lesson 012.4](/learn/012.4), where `*` alone is "anything".

```bash fixture=data-playtest
grep 's.ime' enemies.txt
echo ---
grep '^[sb]' enemies.txt
echo ---
grep 't$' enemies.txt
echo ---
grep 'go*blin' enemies.txt
```

```output
slime
slime
slime
---
slime
bat
slime
bat
slime
skeleton
---
bat
bat
ghost
---
goblin
goblin
```

A `*` may also match **nothing**: `a*` accepts zero `a`s. So the pattern `a*b` matches a line that merely contains `b`, because "zero `a`s, then `b`" is enough. Add both anchors, or use `-x` (the whole line must match), and the pattern becomes strict:

```bash
printf 'aab\nb\nxb\nab\n' | grep -x 'a*b'
```

```output
aab
b
ab
```

`xb` is missing because `x` is neither an `a` nor the `b`. To trace such a pattern, go left to right through the line and ask what each piece of the pattern can take: zero or more `a`s, then exactly one `b`, then the end.

`^[sb]` means "a line that starts with `s` or `b`". Note that `Skeleton` (capital S) is not in the list, because `[sb]` is case-sensitive. `[sS]` would match both.

### Extended regular expressions: grep -E

The 2.0 objectives use **Extended Regular Expression** (ERE) syntax. It's the same idea, with a few more special characters that work without a backslash. You switch it on with `grep -E`. The one to know here is `?`, which makes the item before it **optional** (zero or one time). In ERE, `|` means "or" and `( )` group things:

| ERE pattern | Matches |
|---|---|
| `ghosts?` | `ghost` and `ghosts` (the `s` is optional) |
| `ro+t` | `rot`, `root`, `rooot` (`+` is "one or more") |

Two more operators: a vertical bar between alternatives means "or" (`bat|ghost` matches a line with `bat` or `ghost`), and round brackets group (`^(slime|bat)$` matches exactly `slime` or exactly `bat`).

```bash fixture=data-playtest
grep -E 'ghosts?' enemies.txt
echo ---
grep -E 'bat|ghost' enemies.txt
echo ---
grep -E '^(slime|bat)$' enemies.txt
```

```output
ghost
ghosts
---
bat
bat
ghost
ghosts
---
slime
bat
slime
bat
slime
```

Without `-E`, the same `?` is just an ordinary question mark. This is the usual surprise: `grep 'ghosts?'` finds nothing, because no line contains a literal `?`:

```bash fixture=data-playtest
grep 'ghosts?' enemies.txt
echo "exit status: $?"
```

```output
exit status: 1
```

`grep` exits with 1 when nothing matched (0 means at least one line matched). `egrep` is an old name for `grep -E`; it still works, but write `grep -E`.

Quote ERE patterns in single quotes, or the shell sees the `|`, `(`, `)` and `?` itself.

</ExamOnly>

### Basic regular expressions: plain grep

The 1.6 objectives ask for **Basic Regular Expressions** (BRE), which is what plain `grep` (no `-E`) uses. `.`, `[ ]` and `*` work exactly as shown above. What differs is `?`, and a few siblings (`+`, `|`, `( )`, `{ }`). In **basic** syntax, GNU `grep` treats them as **ordinary characters**, unless you put a **backslash** before them. So `?` as a plain character, and `\?` as the "optional" operator:

```bash fixture=data-playtest
grep 'ghosts\?' enemies.txt
echo ---
grep 'ghosts?' enemies.txt
echo "exit status: $?"
```

```output
ghost
ghosts
---
exit status: 1
```

The first pattern means `ghost` and then an optional `s`. The second searches for the literal text `ghosts?`, which isn't in the file. Writing `grep -E 'ghosts?'` gives the same result as `grep 'ghosts\?'`, which is how you can tell which exam you are reading about: only the 2.0 objectives name `-E`. The `*` needs no backslash in either syntax, so `go*blin` works with plain `grep`.

When a question on the old exam says "regular expression" it means this basic syntax, so a bare `?` in a plain `grep` is not an operator there.

</ExamOnly>

## At TuxPixel

- **The nightly build.** Ada's build runs overnight and writes everything to `build.log`. Every morning Mira runs `grep -c ERROR build.log`. If the number isn't 0, she runs `grep -n ERROR build.log` to find the lines.

- **Who is working on what.** `grep -r "TODO" ~/projects` lists every TODO note in the code, with the file name in front.

## Exam traps

<Callout title="> replaces, >> appends">
  <p>`>` overwrites the file (or creates it) and `>>` adds to the end. Neither shows anything on screen: the output went to the file. `>` is short for `1>`.</p>
</Callout>

<Callout title="Stream numbers: 0, 1, 2">
  <p>0 is stdin, 1 is stdout, 2 is stderr. `2>` redirects errors, and `2>&1` sends errors where standard output goes. Plain `>` never catches error messages. Write `> file 2>&1`, not `2>&1 > file`; the second leaves the errors on the screen.</p>
</Callout>

<Callout title="Pipe or redirect?">
  <p>`|` connects a command to **another command**; `>` and `<` connect a command to a **file**. `ls | file.txt` is an error ("file.txt" isn't a command), and `ls > file.txt` is what you meant. `/dev/null` is the "discard" file: `command > /dev/null` hides normal output.</p>
</Callout>

<Callout title="head and tail are the first and the last">
  <p>`head` prints the start of a file and `tail` the end; both show 10 lines unless you give `-n`. `tail -n 3` is the last three lines. `wc -l` counts lines, `wc -w` words and `wc -c` bytes. `less` is for reading long files; `q` quits it.</p>
</Callout>

<Callout title="sort -n for numbers; -k and -t for fields">
  <p>Without `-n`, `sort` sorts as text, so `10` comes before `9`. `-k2` sorts by the second field, and `-t,` makes the comma the separator. `-r` reverses. `cut` also has a separator option, `-d` (not `-t`), and it picks fields with `-f`. Its default separator is the Tab.</p>
</Callout>

<Callout title="* can match zero times">
  <p>In a regular expression `*` means "the previous item, zero or more times". `go*blin` matches `gblin`, and `a*b` matches any line with a `b` in it. Quote patterns in single quotes so the shell doesn't try to treat `*` as a file glob.</p>
</Callout>

<Callout title="uniq only removes neighbours">
  <p>`uniq` compares each line with the previous one, so unsorted input keeps its duplicates. Use `sort | uniq`. `uniq -c` prefixes each line with its count. And remember: `grep -E` turns on extended regular expressions, where `?`, `+`, `|` and `( )` are operators. Without `-E` they are ordinary characters.</p>
</Callout>

<Callout title="Regex * is not glob *">
  <p>In a regular expression, `.` is any one character and `*` repeats the item before it, so `.*` means "anything". In a file glob (`ls *.txt`), `*` alone means "anything" and `?` means one character. Don't mix the two languages: regular expressions are used by `grep`, globs by the shell.</p>
</Callout>

<Callout title="grep options to remember">
  <p>`-i` ignores case, `-v` inverts (lines that don't match), `-c` counts matching lines, `-n` shows line numbers, `-r` searches a directory tree. `grep` with no match exits with status 1.</p>
</Callout>

## Try it

Open the [terminal](/terminal) and practise with the system's own files:

1. Run `ls /etc > ~/etc-list.txt`, then `wc -l ~/etc-list.txt`. How many names are in `/etc`?
2. Run `cat /etc/passwd | cut -d: -f1 | sort`. That's every user name on the machine (the separator in this file is `:`).
3. Count the users whose login shell is bash: `grep -c bash /etc/passwd`.
4. Make the terminal complain: `ls /nonexistent`. Then redirect the error with `2> errors.txt` and read the file.
5. Look at a long file with `less /etc/services`. Search with `/ssh`, press `n` for the next match and `q` to quit.
6. Find the lines of `/etc/passwd` that start with `r` or `m` with `grep '^[rm]' /etc/passwd`.
7. On exam 010-200, check what `grep -E 'ro+t' /etc/passwd` prints, and why `grep 'ro+t'` doesn't.

When you're ready, [practise this objective](/practice?objective=013.2). Next, turn command lines into scripts in [lesson 013.3](/learn/013.3).
